# RustWTM 0.13.0 system review

Review date: 2026-10-20. Starting revision: `1968fd3`; working tree was clean.
This is a workspace architecture and product review with executable validation,
not a claim that every Win32 failure or hardware combination was exercised.

## System assessment

| Area | Source reviewed | Assessment and next step |
| --- | --- | --- |
| OS access | `wtm-sys/src/{system,process,control,job,gpu,pipe,security}.rs` | Win32 and unsafe code are isolated. Keep device access behind the same boundary. Per-core sampling currently documents a processor-group limit; test machines above 64 logical CPUs before extending support claims. |
| Process identity and actions | `wtm-core/src/{model,sampler,tree,control}.rs` | Sampling and control use PID plus creation time. Frozen rows preserve this identity. Keep all new mutating actions behind the existing control checks. |
| Policy | `wtm-policy/src/{config,governor,memory_guard,limits,swarm,rules,cooling}.rs` | Pure policy is separated from execution. Cooling adds finite/fresh temperature requirements, validated curves, full-speed thermal override and bounded downward changes. |
| Service and history | `wtm-service/src/{engine,executor,app_limits,history,ipc_server,telegram,hardware}.rs` | Cooling runs on a separate worker with provider-owned leases; no hardware write runs in a UI frame. Physical rollback behavior still needs hardware validation. |
| IPC | `wtm-ipc/src/lib.rs` | Protocol 10 adds hardware reports and administrator-only cooling requests. Hello retains its enum tag so older peers reject the version cleanly. Coordinated client/service upgrade required. |
| GUI | `wtm-gui/src/{app,backend,processes,overview,theme,views,settings}.rs` | Strong functional coverage; this release concentrates on navigation, readable themes, stable inspection and short-window usability. Remaining layout and latency work should be measured. |
| CLI and delivery | `wtm-cli`, root manifests, CI/release workflows, installer and documentation | CLI and real child-process tests belong in the workspace gate. Installer/SCM and publication are separate gates; a local test pass does not certify either. |

## Delivered in this change

- Grouped navigation with vector icons, accessible button names even when
  collapsed, an active marker, and page titles/subtitles.
- Refined dark and light surfaces, typography, installed Windows font fallback,
  named theme controls and tested contrast of resource/secondary text against
  the panel/card backgrounds. Chart colours retain their resource identity.
- Scrollable overview/configuration pages and process details; details can be
  closed without leaving Processes. The last metric row fills its width.
- Pause/Resume updates (F6) retains a process-table snapshot. Monitoring,
  service protection and alerts keep running; details and managed labels remain
  live. This is **not** process suspension. Pause/filter state is transient;
  existing saved view/column/sort preferences remain compatible.
- High CPU (>=5%, idle excluded), high private working set (>=512 MiB) and managed
  filters, combined with search. App view groups the matching instances.
  Executable paths are searchable. Counts and a clear-filter empty state make
  partial results explicit. Columns scroll horizontally.
- Fixed duplicate Delete handling at the application level. The permanent UI
  regression test was first run on the original implementation: Delete in
  search incorrectly opened an End task confirmation. The control case (Delete
  from the process table) worked before and after. The same test passes after
  removing the duplicate handler.
- Optional GPU visual-review test renders Overview, Processes, Performance, Sensors and
  Settings at 1440x1000 and the minimum 820x500 window size, in both themes,
  using synthetic service data. Images go to `target/visual-review/`.

The previously committed stuck-swarm work is retained in the 0.13.0 changelog;
it was not implemented by this review.

## Sensors and cooling: implemented continuation

The Sensors workspace now shows device-grouped readings, min/max and recent
history, filters, provider identity and sample age. Missing values remain
unknown. The packaged, self-contained LibreHardwareMonitor 0.9.6 helper uses a
bounded JSON-lines protocol with correlated replies; an absent helper permits
read-only NVIDIA driver fallback. `wtm sensors --json` reads locally.

Cooling has hardware-default, manual and editable curve modes, three presets,
fresh-temperature and finite-value validation, 30% minimum duty, 100% emergency
capability, thermal override, deadband and bounded downward changes. Writes
require an administrator client, an enforcing service and explicit GUI
confirmation. Drafts persist without being applied on startup. Service/provider
work runs separately from process sampling. The provider attempts default
restoration on lease expiry, closed input and normal shutdown; a hung hardware
call or crashed helper can prevent recovery. Named pump controls are disabled;
physical wiring cannot be inferred from firmware labels.

Live read-only discovery on the local RTX 5080 reported GPU/memory-junction
temperature, power, voltage, clocks, fan RPM and three GPU control channels.
The non-elevated probe correctly disabled writes. Detailed CPU/motherboard
access and physical fan control remain unverified. No physical fan write or
separate driver installation was performed. See [hardware setup, architecture
and validation limits](hardware.md) for the full contract and primary sources.

## Validation and boundaries

See the final validation record appended below. The initial unmodified workspace
run failed `app_limits::tests::limits_apps_with_their_children_and_lifts_on_change`
at its orphan-member assertion, and reproduced in subsequent workspace and
service runs. Diagnostics showed that a supposedly retained ping child had
actually exited: the fixture treated a PID in a snapshot as readiness, then
changed jobs and ended its parent during startup. The fixture now starts hidden,
disables cmd AutoRun and waits for an actual loopback reply before testing
ownership. It explicitly waits for ping children (not a console host), requires
both children, and removes the arbitrary 300 ms sleep. Output is read as bytes
so the readiness check does not depend on Windows text encoding. The original
orphan-membership assertion remains; three consecutive complete service-unit
runs passed (61 passed, 1 ignored each). No production limit logic was changed.

`RUSTWTM_SCM_TESTS` was not enabled: the nominal SCM test returns without running
its install/start/stop/uninstall body. Two engine integration tests also return
early when an installed RustWTM service exists, as on this machine. Ignored
tests and gated bodies must not be
counted as live service, Telegram, updater or installer verification. GPU renders
exercise the egui application on synthetic data, not native window chrome/UAC.
